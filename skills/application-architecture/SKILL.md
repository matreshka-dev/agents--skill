# Application Architecture

## 1. Назначение

Этот Skill определяет принципы организации кода приложений на Matreshka.

Основные цели:

- разделение приложения на функциональные области;
- явное определение владельцев модулей и их ответственности;
- локализация связанных частей функциональности;
- независимость приложений внутри одного репозитория;
- контролируемое повторное использование кода;
- минимизация ненужных абстракций и уровней вложенности;
- удобная навигация по проекту как для разработчиков, так и для ИИ-агентов.

Не воспринимай приведённые структуры как обязательные шаблоны. Выбирай минимальную организацию, которая соответствует реальным границам ответственности проекта.

## 2. Основные архитектурные принципы

### 2.1. Определяй владельца кода

Перед размещением модуля определи, кому он принадлежит:

- **Application** — конкретному приложению.
- **Feature** — функциональной или предметной области.
- **Entry** — конкретной самостоятельной точке входа.
- **Shared** — общей области приложения.
- **Package** — независимому модулю, используемому несколькими приложениями.
- **Theme** — визуальной системе приложения.

Владелец определяет расположение модуля, его жизненный цикл и допустимые зависимости.

Не определяй расположение файла исключительно по его техническому типу.

Например, Context, используемый только одной страницей, должен находиться рядом с этой страницей, а не в глобальном каталоге Context.

### 2.2. Сохраняй локальность функциональности

Связанные части одной функциональности должны находиться рядом:

- Entry Component;
- Context;
- схемы и типы;
- модель и логика;
- представление;
- локальные компоненты.

Не разбрасывай связанные модули по глобальным каталогам `types`, `schemas`, `contexts`, `models` и `utils`.

При этом не объединяй всё в один большой файл. Разделяй модули по самостоятельным ответственностям и причинам изменения.

### 2.3. Не создавай абстракции без необходимости

Не создавай дополнительные уровни каталогов, интерфейсы, фабрики, barrel-файлы и универсальные модули только ради формального единообразия.

Выноси код в отдельную область или пакет, если для этого существует реальная архитектурная причина.

### 2.4. Учитывай навигацию ИИ-агентов

Структура должна позволять быстро определить:

- назначение файла;
- его владельца;
- связанные с ним модули;
- направление зависимостей.

Предпочитай понятные предметные названия файлов и прямые импорты.

Избегай универсальных файлов-свалок и чрезмерного дробления небольших связанных частей кода.

## 3. Структура репозитория

Репозиторий может содержать одно или несколько самостоятельных приложений.

Не предполагай, что весь репозиторий представляет собой одно приложение.

### 3.1. Несколько приложений

Для нескольких приложений используй отдельную область каждого приложения:

```text
repository/
  apps/
    application-a/
      app/
      features/
      shared/
      theme/

    application-b/
      app/
      features/
      shared/
      theme/

  packages/
    package-a/
    package-b/
```

Это концептуальный пример. Если репозиторий уже использует другую организацию workspace, сохраняй существующие соглашения.

Каждое самостоятельное приложение имеет собственные:

- конфигурацию;
- маршрутизацию;
- инфраструктуру аутентификации;
- shell и layout;
- глобальные Context;
- Features;
- тему и визуальные ресурсы;
- настройки окружения.

Не объединяй инфраструктуру нескольких приложений в один глобальный слой, если у приложений различаются точки входа, жизненный цикл, конфигурация или поведение.

### 3.2. Независимость приложений

Приложения должны оставаться самостоятельными единицами.

Не используй внутренние файлы одного приложения напрямую из другого.

Если функциональность действительно общая, выдели её в отдельный пакет с понятным публичным API.

Не связывай приложения через случайные относительные импорты между их каталогами.

### 3.3. Два уровня Shared

Различай:

**Application Shared**

```text
apps/
  application-a/
    shared/
```

Содержит код, который используется несколькими Features одного приложения.

**Workspace Packages**

```text
packages/
  package-a/
```

Содержат независимые модули, которые используются несколькими приложениями или имеют самостоятельную границу публикации и версионирования.

Не поднимай код из Application Shared в Workspace Package только ради потенциального повторного использования.

Для выделения пакета должны существовать реальные потребители, самостоятельная ответственность и понятный публичный контракт.

Не создавай один глобальный `shared/` для всех приложений.

## 4. Структура приложения

Внутри каждого приложения используй feature-first организацию:

```text
application/
  app/
    config/
    routes/
    routing/
    auth/
    shell/
    contexts/

  features/
    feature-a/
    feature-b/

  shared/

  theme/
```

Создавай только необходимые каталоги.

### 4.1. App

`app/` содержит инфраструктуру и композицию конкретного приложения:

- конфигурацию;
- таблицы маршрутов;
- механизмы маршрутизации;
- инфраструктуру аутентификации;
- shell и layout;
- глобальные Context;
- инициализацию приложения;
- связывание основных частей приложения.

`app/` не должен становиться местом для бизнес-логики всех Features.

### 4.2. Features

`features/` содержит функциональные и предметные области приложения.

Feature может включать:

- Entry Components;
- локальные компоненты;
- Context;
- модели;
- бизнес-логику;
- вспомогательные функции;
- типы и схемы.

Feature должна быть максимально самостоятельной в рамках архитектуры приложения.

Не создавай Feature только ради группировки нескольких технически похожих файлов.

### 4.3. Shared

`shared/` содержит действительно общую функциональность приложения.

Модуль относится к Shared, если он используется несколькими независимыми Features и не принадлежит исключительно одной из них.

Не переноси код в Shared только потому, что он кажется потенциально универсальным.

## 5. Entry Components

Entry Component — самостоятельная точка входа в интерфейс.

К ним относятся:

- Page;
- Dialog;
- Popover;
- другие самостоятельные компоненты, имеющие собственный жизненный цикл.

Entry Component может владеть:

- lifecycle;
- Context;
- представлением;
- логикой сценария;
- локальными компонентами.

Пример организации:

```text
feature/
  entries/
    pages/
      list/
        page.ts
        context.ts
        model.ts
        view.ts
    dialogs/
      edit/
        dialog.ts
        context.ts
        model.ts
        view.ts
```

`page.ts` и `dialog.ts` — хаб. В них остаются класс Entry, lifecycle (`boot`, `onEnter`, `onLeave`, `onScroll`), конструктор и вызовы соседних модулей. Определение контекста, сценарии и дерево компонентов в хабе не пишутся.

### Правила размещения

1. Код, используемый только одним Entry, размещай внутри его каталога.
2. Локальные компоненты Entry размещай рядом с ним.
3. Компоненты, используемые несколькими Entry одной Feature, размещай на уровне Feature.
4. Компоненты, используемые несколькими Features, размещай в Application Shared.
5. Самостоятельные Dialog и Popover размещай в области их реального использования.
6. Не превращай Entry в монолит: контекст, модель и вёрстка — отдельные файлы рядом с хабом.

Дальше `view.ts` не дели. Запрет дробить DSL относится к разрезанию уже выделенного представления на файл ради каждого узла. Дели `view.ts` на несколько файлов только если части меняются независимо.

## 6. Context

Context — механизм состояния, реактивности, синхронизации и валидации Matreshka.

Его расположение определяется владельцем и жизненным циклом.

### 6.1. Области владения

Различай:

- **Entry Context** — принадлежит конкретному Entry.
- **Feature Context** — используется несколькими Entry одной Feature.
- **App Context** — принадлежит приложению.
- **Shared Context** — используется несколькими независимыми областями.

Владелец Context отвечает за его создание и уничтожение.

Entry не должен уничтожать Context, которым он не владеет.

Если Context используется несколькими Entry, его жизненный цикл должен быть независим от жизненного цикла одного из них.

### 6.2. Организация файлов

Если у Entry один Context, держи его в `context.ts` рядом с хабом, а не внутри `page.ts` или `dialog.ts`:

```text
entry/
  entry.ts
  context.ts
  model.ts
  view.ts
```

`context.ts` содержит тип значения, Zod-схему этого Entry и фабрику `createContext`. Хаб создаёт экземпляр (`entryContext(createEntryContext(...))` или `Context.create` в `static create`) и вызывает `init` в lifecycle. Колбэк загрузки передаётся в фабрику и выполняется моделью позже, уже после конструктора.

Если Context несколько:

```text
entry/
  entry.ts
  model.ts
  contexts/
    primary-context.ts
    filter-context.ts
    selection-context.ts
  view/
```

Если Context используется несколькими Entry одной Feature:

```text
feature/
  contexts/
```

Если Context принадлежит приложению:

```text
app/
  contexts/
```

Если Context действительно общий для нескольких Features:

```text
shared/
  contexts/
```

Не создавай каталог `contexts/` только ради одного небольшого Context, если отдельный файл рядом с Entry понятнее.

### 6.3. Схемы, типы и фабрики

По умолчанию размещай рядом:

- Zod schema;
- связанный TypeScript type;
- фабрику Context.

Не разделяй их на отдельные файлы без необходимости.

Выноси схему отдельно, если она большая, используется несколькими независимыми модулями или представляет самостоятельный контракт.

Различай:

- Context Definition — описание структуры и ограничений данных;
- Context Factory — создание Context;
- Context Instance — конкретный экземпляр Context.

Не создавай глобальные каталоги схем и типов исключительно ради технической классификации.

## 7. Model, Lib и Utils

### 7.1. Model

`model.ts` внутри Entry содержит логику конкретного Entry. Эти функции не остаются приватными методами класса страницы или диалога:

- загрузку и подготовку данных;
- фильтрацию и сортировку;
- пагинацию;
- подписки на события;
- обработку сценариев;
- координацию Context и сервисов.

На уровне Feature каталог `model/` может содержать предметную логику, используемую несколькими Entry.

`model` — не синоним вспомогательных функций.

### 7.2. Lib

`lib/` предназначен для самостоятельных вспомогательных модулей, которые не являются моделью конкретного Entry или Feature.

Например:

- форматирование;
- преобразование данных;
- независимые вычисления;
- функции общего назначения в пределах владельца.

### 7.3. Utils

Не используй `utils/` как универсальное место для кода, которому пока не нашли владельца.

Предпочитай размещение по смысловой ответственности.

Например, функции аутентификации должны находиться в области аутентификации, а не в универсальном каталоге утилит.

## 8. Client Settings и конфигурация приложения

ClientSettings — конфигурация конкретного приложения Matreshka.

В репозитории с несколькими приложениями каждое самостоятельное приложение должно собирать собственный объект ClientSettings.

Рекомендуемое расположение:

```text
apps/
  application-a/
    app/
      config/
        client-settings.ts

  application-b/
    app/
      config/
        client-settings.ts
```

Не используй итоговый объект ClientSettings одного приложения как конфигурацию другого приложения.

Даже если приложения используют одинаковые визуальные ресурсы, каждое приложение самостоятельно собирает свою конфигурацию.

### 8.1. ClientSettings как точка композиции

Файл ClientSettings собирает настройки приложения из тематических и конфигурационных модулей.

В нём могут находиться:

- метаданные приложения;
- ссылки на ресурсы приложения;
- конфигурация шрифтов;
- реестры визуальных токенов;
- другие настройки, необходимые клиенту.

Не размещай в нём реализацию самих токенов или бизнес-логику.

### 8.2. Theme

`theme/` принадлежит конкретному приложению.

В нём размещаются:

- цветовые токены;
- шрифты;
- общие стили;
- визуальные primitives;
- другие ресурсы дизайн-системы приложения.

Например:

```text
theme/
  colors/
    tokens/
    index.ts

  fonts/
    index.ts

  styles/
```

Тематические модули могут собирать реестры токенов, которые затем используются в ClientSettings.

Не смешивай определение токенов с их регистрацией в ClientSettings.

Не создавай отдельный файл для каждой константы, если логически связанные определения удобнее поддерживать вместе.

### 8.3. Общая тема нескольких приложений

Не предполагай, что все приложения должны использовать одну глобальную тему.

У приложений могут быть разные визуальные системы, наборы токенов и шрифтов.

Если несколько приложений действительно используют общие визуальные primitives, можно выделить их в отдельный пакет. При этом каждое приложение должно сохранять возможность собирать собственную тему и конфигурацию.

Настройки, зависящие от окружения, должны обрабатываться на уровне конфигурации приложения, а не внутри определений дизайн-токенов.

## 9. Маршрутизация и доступ

Маршрутизация относится к Application, поскольку связывает URL с Entry Components и обеспечивает навигацию приложения.

Различай:

- таблицы маршрутов;
- механизмы разрешения страниц;
- аутентификацию;
- авторизацию;
- проверки доступа к сущностям.

Рекомендуемая структура:

```text
app/
  routes/
  routing/
  auth/
```

### 9.1. Routes

`routes/` содержит таблицы маршрутов конкретного приложения и связывает маршруты с Entry Components.

Не размещай здесь бизнес-логику страниц.

### 9.2. Routing

`routing/` содержит общие механизмы маршрутизации:

- Page Handlers;
- проверки принадлежности маршрута приложению;
- защищённые маршруты;
- общую обработку сущностных маршрутов;
- fallback и разрешение страниц.

Не дублируй одинаковые механизмы в каждой таблице маршрутов.

### 9.3. Auth

`auth/` содержит инфраструктуру аутентификации:

- работу с сессией;
- работу с токенами;
- получение текущего пользователя;
- сброс сессии;
- общие механизмы проверки аутентификации.

Если реализация используется только одним небольшим модулем, не выноси её в отдельный каталог без необходимости.

### 9.4. Предметные правила доступа

Разделяй механизм проверки и сами правила.

- Механизм проверки при открытии маршрута относится к `app/routing/`.
- Инфраструктура сессии относится к `app/auth/`.
- Предметные определения ролей, прав и требований относятся к соответствующей Feature или предметной области.

Не помещай все определения прав в маршрутизацию только потому, что маршруты используют их.

### 9.5. Серверная безопасность

Проверки на уровне маршрутов не заменяют серверную авторизацию.

Каждая серверная операция и каждый доступ к защищённым данным должны самостоятельно проверять необходимые права.

Успешное открытие страницы не является доказательством права выполнить серверную операцию.

## 10. Shell и глобальные контексты

`app/shell/` содержит оболочку приложения:

- layout;
- навигацию;
- общие меню;
- header;
- другие элементы каркаса приложения.

Не размещай здесь содержимое отдельных Features.

Глобальные Context размещай в `app/contexts/`, если их владельцем действительно является приложение.

Context конкретной Feature или Entry должен оставаться у своего владельца.

## 11. Зависимости между областями

Соблюдай следующие направления зависимостей:

- Application может связывать и конфигурировать Features.
- Feature не должна зависеть от внутренней реализации другой Feature без необходимости.
- Shared не должен зависеть от Features.
- Workspace Package не должен зависеть от конкретного приложения.
- Одно приложение не должно импортировать внутренние файлы другого приложения.
- Межприложенческое повторное использование должно проходить через явно определённые пакеты и публичные API.

Избегай циклических зависимостей.

Не создавай barrel exports автоматически для каждого каталога. Публичные точки входа нужны там, где они задают реальную границу модуля.

## 12. Алгоритм архитектурного решения

Перед созданием файлов или реорганизацией кода выполни следующие шаги.

1. **Определи приложение.** К какому приложению относится функциональность? Используется ли она в нескольких приложениях?
2. **Определи владельца.** Это Application, Feature, Entry, Shared, Package или Theme?
3. **Определи точку входа.** Есть ли самостоятельный Entry Component?
4. **Определи Context.** Сколько Context необходимо, кто ими владеет и каков их жизненный цикл?
5. **Раздели ответственность.** Что относится к представлению, модели, конфигурации, теме или инфраструктуре?
6. **Проверь повторное использование.** Используется ли код несколькими Features или приложениями реально, а не гипотетически?
7. **Выбери минимальную структуру.** Создавай только необходимые файлы и каталоги.
8. **Проверь зависимости.** Нет ли циклов и зависимости общих модулей от конкретных Features или приложений?
9. **Проверь lifecycle.** Не уничтожает ли Entry ресурс, которым он не владеет?
10. **Сохрани существующие соглашения.** Не перестраивай весь проект, если задача требует локального изменения.

Если существующая структура уже понятна и соответствует этим принципам, не меняй её ради формального совпадения с примерами.

## 13. Антипаттерны

Избегай:

- предположения, что репозиторий содержит только одно приложение;
- единого глобального `app/` для нескольких самостоятельных приложений;
- единого глобального `shared/` для несвязанных приложений;
- прямого импорта внутренних файлов одного приложения другим;
- выделения пакетов без реального межприложенческого использования;
- глобальных каталогов `contexts/`, `schemas/`, `types/`, `models/` и `utils/`, смешивающих разные Features;
- переноса кода в Shared без реального общего использования;
- чрезмерно больших Entry Components, в которых контекст, сценарий и дерево DSL написаны внутри `page.ts` или `dialog.ts`;
- чрезмерного дробления уже выделенного `view.ts` и небольших функций;
- смешивания `model.ts` и `utils.ts`;
- смешивания ClientSettings с определениями дизайн-токенов;
- одной общей темы для всех приложений без общей дизайн-системы;
- размещения бизнес-правил доступа в инфраструктуре маршрутизации;
- предположения, что route guard заменяет серверную проверку прав;
- уничтожения общего Context при уничтожении одного Entry;
- создания абстракций и файлов «на будущее».

## 14. Поведение ИИ-агента

При архитектурных задачах:

1. Изучи структуру репозитория и локальные инструкции.
2. Определи количество приложений и границы workspace.
3. Найди ближайшие аналогичные Features и Entry Components.
4. Определи владельца новой или изменяемой функциональности.
5. Выбери структуру, соответствующую существующим соглашениям и принципам Skill.
6. Не выполняй массовую реорганизацию несвязанных частей проекта.
7. Не создавай каталоги и файлы без конкретной необходимости.
8. При существенном архитектурном выборе кратко объясни причину выбранного уровня владения.
9. Сохраняй существующие публичные API и поведение, если задача явно не требует их изменения.

При обычной задаче разработки применяй эти правила локально. Не нужно каждый раз описывать всю архитектуру или перестраивать проект.
